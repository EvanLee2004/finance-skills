## A. 三个缺陷（都能写坏她的表 / 藏错）

### A1 ⭐ 写入环没有二次身份复核（最严重）

**病灶**：`validate_plan` 会复核「第 N 行还是不是那个 SOD」，但 `apply_to_copy`
**直接按行号写**，中间隔着一次**人工确认**——她看《核销日清》可能几分钟，也可能隔天才回你
一句「确认」。而 `--in-place` 写的正是她天天在用的那份表。

- 月初贴交付会**插行**、部分核销会在上方**插行**（文档自己写过的高发场景）
- 插一行 → 行号全部错位 → 这一笔的五列写到**别人那一单**上
- 更糟：`write_plan` 还会写 **SOD 列**，等于把那行的单号也覆盖掉
- 而 `verify_written` 只比五列、**不比 SOD**，所以照样报「写后回读逐格比对：全部一致 ✓」

**修**：
1. `validate` 把「校验那一刻」的 **盈亏副本 sha256 + 每行 SO/SOD 身份**写进计划
2. 新增 `apply_to_copy.precheck_before_write()`：写之前比指纹 + 逐行复核身份 + 重跑
   `check_one`，**任一条不过 → 整批拒写**（不是跳过那一条：插一行会让它之后的全错位）
3. `verify_written` **把 SOD 纳入回读比对**

### A2 幂等对「计划留空」太宽松

`same` 用 `if five.get(k) is not None` 跳过留空列 → 「表里计提=1000、本次算的是留空」
被判成 `skip`「已填过且一致」，**静默放过**。而「计提该不该填」正是明妹口径里最容易错的一条
（回款明细合计 = 交付额才可填）。**修**：计划留空但表里有值 → 报冲突进日清。

### A3 流转写入同病

准入（强三键唯一命中）是在 `build_flow_plan` 那一刻算的，写入之间同样隔着确认，
而流转表是**每天往里加行的活表**。**修**：命中行的 **日期/公司名称/金额** 记进计划，
`apply_flow` 写前复核；对不上 → **整批不写流转**。

## B. 日期口径：两个日期 + 漏天检测

### B1 问题：这条链路有两个互不相干的日期

| 日期 | 含义 | 驱动 |
|---|---|---|
| 到账日期 | 钱哪天到银行 | 第 1–4 步 |
| **核销日期** | 销售哪天在智云把钱核到订单上 | **第 6 步起（主战场）** |

她的口径原话：「与建回款无固定隔天关系；核了就进那个核销日」→ **天然不是同一天**。
旧版 SKILL 只有一句 `--date yesterday`，把两件事混着叫「昨天」。

### B2 比"要不要确认"更严重的：**会静默漏天**

`yesterday` 是相对**运行那天**算的：

- 周一跑 → 取周日（销售周末不核销，必空批）；周二跑 → 取周一
  → **周六/周日/周一之间漏掉的核销日永远没人管，程序一声不吭**
- 她请假两天、出差一周、系统故障没跑，同理
- 漏一天 = 那天的到账**永远不会回填进盈亏表**，而且事后**没有任何地方看得出来**

### B3 修法（三件套）

1. **日期显式化**：`common.resolve_batch_date` 把相对说法解析成具体某天；
   `date_cn()` 输出「2026-07-24（周五）」供 SKILL 复述确认；
   **所有产出与文件名按核销日命名**（补跑 7-22 才不会跟今天那批撞名盖掉）
2. **跑批台账 `scripts/batch_ledger.py`**（新）：每个核销日跑到哪一步
   （fetched → classified → listed → applied）登记在 `03_台账/跑批台账.json`；
   `gaps` 子命令报出**从来没跑过**的核销日；`suggest_date` 优先补最早的空档
3. **一批一天**：`classify_hexiao` 发现数据里混着多个核销日 → **直接退出**
   （混批会让 AR 覆盖率、幂等校验和她逐行核对全部失真）；
   `--hexiao-date` 声明她确认的那天，与数据实际不符也退出（防取错日子）

配套：**空批 ≠ 出错**（那天没人核销 = 正常收工，记台账，别反复当漏天提醒）；
漏天起点 = 台账第一次登记那天；周末默认不计入（`--all-days` 可算上）。

## D. 任何 AI 不得回退的点

1. **写入前必须复核**（指纹 + 身份）；复核没过**不许加参数硬写**，正确动作是重出日清让她重新确认。
2. **回读比对必须含 SOD**。
3. **一批只跑一个核销日**；产出按核销日命名。
4. **每次开跑先查漏天再复述日期**——不许默认"昨天"闷头跑。
5. 「计划留空 vs 表里有值」**必须报冲突**，不许当幂等跳过。

## E. 补充（2026-07-25 晚 · 明昊拍板她的真实节奏）

**新事实**：明妹**不天天来**——约**一周两天**、看她哪天有空，一来常积好几天的核销。

**决策：维持"一批一天"，多天由 agent 多跑几遍**（明昊拍板，不做并批）。

理由（唯一硬理由）：同一个订单可能**分两天核销**（7-21 核一半、7-23 核另一半），
两笔要填的是她盈亏表里**同一行**。

- **按天先后跑**：先写 7-21 的，7-23 再来时 validate 看到"已填一半"，接着算 → 对
- **并成一批**：两笔同时命中同一行 → `validate` 的 seen_rows 判「一行被两笔命中」→ 双双挂起 → 白跑

所以**顺序钉死：从早到晚**，不许跳过中间某天直接跑最新的。

**落地（纯壳改动，无判定逻辑变更）**：
1. `SKILL.md §0.45`「补多天：先规划 → 短句确认 → 一天一天跑几遍」+ 路由表加
   「把没跑的都跑了 / 这几天的一起做」
2. `batch_ledger gaps` 末尾多打一行 **【照说这句】**，agent 直接照抄给她，不用自己组织语言
3. `references/跟明妹沟通.md` 新增〇节：只有一天 / 积了好几天 / 跑到第几天 / 空批 / 她喊停 五种短话术
4. `config/业务规则.md` 记「她的节奏」与「补多天顺序从早到晚」
5. **说话要更短**：她是出纳，⛔ 别解释原理、⛔ 别一次抛一堆问题（SKILL §0.6 强化）

**测试**：+3 条（空档从早到晚有序 / 一天天跑完空档逐个消失且中途停不丢 / suggest_date 逐日前进）→ **178 全绿**。

## F. opencode 真实模拟测试（2026-07-25 晚 · 标准规程③）

明昊问「能稳定跑吗、拿 opencode 测过吗」——**此前只跑了 pytest 和直接调脚本，没做这层**。补测，
用金标 13 笔真实数据 + 免费模型 `north-mini-code-free`，把她已填的 143 行五列清空模拟"还没填的一天"。

### 测出来的两个真问题（都已修）

**F1 ⭐ 产出分家 → 流转静默不写**
AI 会 `cd` 进技能目录再传 `--workspace .`，旧版 `ensure_out_dirs` **就地新建四个空目录**：
判定/校验落 `工作区/04_产出/`、日清和流转计划落技能根 `04_产出/`。
真正的伤害不是"文件难找"：她说「确认」时 `apply_all` 按默认工作区找流转计划**找不到**，
于是 **只写盈亏、静默跳过流转、还不报错**。
→ 新增 `common.resolve_workspace()`：给的目录没输入但下面有 `工作区/` 就**自动纠正**并喊一声；
全部脚本改用解析后的工作区；`ensure_out_dirs` 返回解析结果。

**F2 取数在非交互环境卡死**
数据明明已在 `01_智云导出/`，它还是跑 `fetch_zhiyun` → 卡在 `input()` 输账号 → `EOFError` traceback → 整条链断。
→ ① `already_fetched()`：**这天的四件套齐了就跳过取数**（她手导的也算，`--force` 可强制重取）；
② 非交互环境的账密提示改成三条明确出路，不甩 traceback。
> ⚠ **这不是"取数可以省"**（明昊 2026-07-25 明确强调）。取数是必经步骤，只有
> "这天的数据已经取过/她手导过"才跳过；缺文件或换一天照样必须取。

### 顺带修的可用性问题

- `validate_plan` 的 `--plan`/`--ledger` 改成**可不给**（自动找），AI 之前为路径试错 4 次
- `build_flow_plan`/`build_worklist`/`validate_plan` **收下多余的 `--hexiao-date`**（AI 爱顺手传给每个脚本，
  argparse 报错会直接断链）
- **漏天提示嵌进 `classify` 输出**——不能指望编排的 AI 记得先跑 `gaps`（实测它跳过了 §0.4）
- SKILL 命令链改成 `cd` 到技能目录 + 相对脚本名、**不传 `--workspace`**（照抄即可跑）
- **流转写入幂等**：表里已经是这个值就跳过，不重写、不多存备份（此前重跑会再写 11 笔）
